## #1 버퍼 시간이 무시되는 경로가 있다 (버그)

> room-b 는 버퍼가 15분이다. alice 가 화요일 10:00~11:00 을 예약해 둔 상태에서 bob 이 **반복 예약**으로 매주 화요일 11:00~12:00 을 잡았더니 버퍼 없이 바로 붙어서 잡혔다. 같은 시간을 bob 이 단건으로 예약하면 `Conflict` 가 난다. 대기자 승격이나 예약 변경에서도 비슷한 일이 있었다는 제보가 있다. 그리고 `free` 는 버퍼 때문에 실제로는 예약할 수 없는 시작 시각을 보여 주고, 반대로 그 시각에 `wait` 로 대기 등록을 하려 하면 "지금 예약할 수 있는 시간"이라며 거절한다.

기대 동작
- README 의 버퍼 규칙(다른 회원의 예약과는 버퍼 이상 떨어져야 함, 간격이 정확히 버퍼면 됨, 같은 회원의 예약끼리는 겹치지만 않으면 됨, 영업 종료 시각과는 상관없음)이 **예약이 생기거나 예약 시각이 바뀌는 모든 경로**와 **"이 시간이 비었나"를 판단하는 모든 곳**에서 단건 예약과 똑같이 적용되어야 한다.
- 대기 등록: 그 회원이 지금 단건 예약으로 잡을 수 없는 시간(버퍼 때문인 경우 포함)이면 등록되고, 잡을 수 있는 시간이면 지금처럼 `BookingError`.
- 대기자 승격: 승격하면 버퍼 규칙을 어기게 되는 항목은 승격하지 않고 대기열에 남긴다.
- `free_slots`(CLI `free`)는 회원을 모르므로, 버퍼가 있는 자원에서는 그 자원의 **모든** 예약과 버퍼 간격을 지키는 시작 시각만 돌려준다.
- 예: room-b(월~금 08:00-20:00)에 alice 의 화 10:00~11:00 이 있을 때 — bob 의 반복 예약 11:00~12:00 은 `Conflict`(`skip_conflicts=True` 면 그 날짜를 건너뛰고 `exceptions` 에 남김), alice 자신의 반복 예약 11:00~12:00 은 된다. `free_slots("room-b", 그날, 60)` 에는 08:45 와 11:15 가 있고 09:00·10:45·11:00 은 없다.

## #2 자정을 넘는 영업시간 (기능 요청)

> 금요일 밤 해커톤 때문에 `fri 18:00-02:00` 처럼 자정을 넘는 영업시간을 쓰고 싶다. 지금은 "닫는 시각은 여는 시각보다 뒤여야 합니다" 오류가 난다.

기대 동작
- 구간의 닫는 시각이 여는 시각보다 **앞이면** 다음 날 그 시각까지 영업한다. 닫는 시각 `00:00` 은 자정까지라는 뜻이다(`18:00-00:00` = 18:00 ~ 다음 날 00:00). 여는 시각과 닫는 시각이 같으면 지금처럼 `ValueError`.
- 구간은 **여는 날**의 것이다: `fri 18:00-02:00` 은 금 18:00 ~ 토 02:00. 한 요일이 두 번 나오면 지금처럼 `ValueError`. 자정을 넘는 구간이 다음 날의 구간과 겹치면 `ValueError`(맞닿는 것은 된다. 일요일 구간의 다음 날은 월요일).
- 예약은 영업 구간 **하나** 안에 들어가야 한다(맞닿은 두 구간에 걸치는 것도 안 된다). `fri 18:00-02:00` 이면 금 23:00~토 01:00 과 토 00:30~01:30 예약이 된다(토요일에 다른 영업시간이 없어도). 토 01:30~02:30 은 `OutsideHours`.
- 이 규칙은 영업시간을 보는 모든 곳에 똑같다: 단건 예약, 반복 예약(발생마다), 예약 변경, 대기 등록, `free_slots`, 가동률 보고서.
- `free_slots(resource_id, day, minutes)`: **그 날 여는** 구간 안의 시작 시각들이다(자정을 넘은 부분 포함). 전날 구간의 자정 넘은 부분은 그 날의 결과에 넣지 않는다.
- 가동률(`utilization`)의 영업 시간은 실제 시각 기준으로 기간 [start, end) 과 겹치는 부분만 센다. 예: `fri 22:00-02:00` 인 자원의 토요일 하루([토 00:00, 일 00:00)) 영업 시간은 120분.
- `format_hours`, CLI `resources`, 저장 파일은 `fri 18:00-02:00` 처럼 쓴다(읽고 다시 쓰면 같은 문자열).
- 비용·비수기 할인·크레딧 달·취소 알림 시간은 지금처럼 예약 **시작 시각** 기준이다.

## #3 취소 수수료 표 변경과 유예 시간 (운영 정책 변경)

> 운영팀 결정: 수수료 구간을 하나 더 두고, 실수로 잘못 잡은 예약은 바로 취소하면 수수료를 받지 않는다.

기대 동작
- 새 수수료 표(알림 시간 = 예약 시작 − 취소 시각): **48시간 이상 0%**, **24시간 이상 48시간 미만 25%**, 2시간 이상 24시간 미만 50%, 2시간 미만 100%.
- 유예 시간: 예약을 만든 뒤 **15분 이내**(`지금 − created_at ≤ 15분`)에 취소하면 알림 시간과 상관없이 수수료 0.
  반복 예약의 발생은 반복 예약을 만든 시각, 대기에서 승격된 예약은 승격 시각이 `created_at` 이다. 예약 변경(`move`)은 `created_at` 을 바꾸지 않는다(README 그대로).
- 수수료는 지금처럼 청구한 크레딧 기준, 정수로 **올림**: 10 크레딧의 25% → 3, 2 크레딧의 25% → 1.
- 모든 취소 경로(단건 취소, 반복 예약 취소 `cancel_series`, 한 날짜 취소 `skip_occurrence`, CLI)에 똑같이 적용한다. 돌려주는 `Cancellation`, `booking.fee`, 환불액, `cancelled` 알림 글, 청구서의 수수료 줄도 새 규칙의 값이다.

## #4 대기자가 자리를 이어받으면 수수료 면제 (운영 정책 변경, #3 과 함께 적용)

기대 동작
- 취소 때문에 대기자가 승격되어 **취소된 예약의 시간과 겹치는** 예약이 하나라도 생기면, 그 취소의 수수료는 0 이고 청구 크레딧 전액을 환불한다(#3 의 표와 상관없이).
- 승격 규칙은 그대로다(등록 순서, 버퍼를 포함한 충돌 규칙, 크레딧이 모자라면 건너뜀). 승격이 일어났더라도 취소된 시간과 겹치는 예약이 없으면 면제가 아니다.
- 반복 예약 취소와 한 날짜 취소도 발생마다 따진다: 시작 순서대로 발생 하나를 취소하고 → 그 자원의 대기열을 승격하고 → 그 발생의 수수료를 정한다.
- 돌려주는 `Cancellation`, `booking.fee`, 잔액(전액 환불), `cancelled` 알림 글(`수수료 0 · 환불 {청구 크레딧}`), CLI 출력, 청구서 모두 면제된 값이어야 한다.

## #5 팀 크레딧 공유 (기능 요청)

> 스타트업 팀 단위 계약이 늘었다. 팀원들이 팀 크레딧 하나를 함께 쓰게 해 달라.

기대 동작
- 팀: `Space.add_team(team_id, name, monthly_credits, overage_price=None)` → 팀 객체. id 규칙은 회원과 같다. `monthly_credits` 는 0 이상의 정수, `overage_price` 는 `None`(초과 사용 불가) 또는 0 이상의 금액(`str`·`int`·`Decimal`, `Decimal` 로 보관). 형식이 틀리면 `ValueError`, 같은 id 가 있으면 `AlreadyExists`.
  `Space.team(team_id)`(없으면 새 오류 `UnknownTeam` — `NotFound` 하위, `booking` 에서 import), `Space.teams()`(id 순). 팀 객체 속성: `id`, `name`, `monthly_credits`, `overage_price`, `members`(회원 id 의 정렬된 리스트).
- `Space.join_team(member_id, team_id)`: 회원은 팀 하나에만 속한다. 이미 팀에 속해 있으면 `BookingError`. `Space.leave_team(member_id)`: 팀에 없으면 `BookingError`. 회원 객체에 `team` 속성(팀 id 또는 `None`).
- 팀에 속한 회원의 예약은 그 달 크레딧을 **팀 계정**에서 쓴다. 예약이 생기는 모든 경로(단건, 반복, 대기자 승격)가 그렇다. 잔액 검사는 팀 잔액(팀 월 크레딧 − 팀의 그 달 사용)으로, 초과 허용 여부는 팀의 `overage_price` 로 정한다. 회원 개인 잔액은 쓰지도 보지도 않는다. 계정은 예약이 생기는 시점(승격은 승격 시점)의 소속으로 정한다.
- 예약은 청구한 계정을 `Booking.account` 에 남긴다: `"member:<회원 id>"` 또는 `"team:<팀 id>"`. 그 예약의 환불·수수료 정산·차액 청구(#8)는 **언제나 그 계정**으로 간다 — 그 사이 팀을 나가거나 들어갔어도. 팀에 들기 전에 만든 예약은 개인 계정 그대로다.
- 원장 항목에 `account` 속성(같은 형식). `member_id` 는 지금처럼 예약한 회원.
- `Space.balance(member_id, month)` 는 지금처럼 회원 **개인 계정**의 잔액이다. 새 `Space.team_balance(team_id, month)` = 팀 월 크레딧 − 팀 계정의 그 달 (청구 − 환불).
- 청구서: `invoices.invoice(space, member_id, month)` 는 **개인 계정으로 청구된** 예약만 넣는다. 새 `invoices.team_invoice(space, team_id, month)` 는 팀 계정으로 청구된 예약(누가 예약했든)으로 만들고, 줄 글 끝에 `" (회원 id)"` 를 붙인다(`Room A 09:00-10:00 (alice)`, `취소 수수료 Room A 14:00-15:00 (bob)`). `owner` 는 `"team:<팀 id>"`, `plan` 은 `"team"`, `allowance` 는 팀 월 크레딧, 금액 = 초과 × 팀 `overage_price`(없으면 0.00). `render_invoice` 는 같은 형식이므로 첫 줄은 `청구서 2026-10 · team:core (team)`.
- 보고서: `reports.credit_usage` 는 지금처럼 회원 개인 계정만 센다. 새 `reports.team_usage(space, month)` → 팀 id 순으로 `team_id`, `allowance`, `used`, `balance` 속성을 가진 행.
- CLI(새 명령, 기존 명령의 출력 형식은 그대로):
  - `team-add ID NAME CREDITS [--overage PRICE]`, `team-join MEMBER TEAM`, `team-leave MEMBER` — 출력 없음.
  - `teams` → 팀마다 `ID<TAB>NAME<TAB>CREDITS<TAB>OVERAGE<TAB>MEMBERS` (OVERAGE 는 소수 둘째 자리 금액 또는 `-`, MEMBERS 는 회원 id 를 정렬해 쉼표로 이은 것, 없으면 빈 문자열).
  - `team-balance TEAM [--month YYYY-MM]` → `TEAM<TAB>MONTH<TAB>ALLOWANCE<TAB>USED<TAB>BALANCE` (월 기본값은 `--now` 의 달).
  - `team-invoice TEAM MONTH` → `render_invoice` 형식.
- 저장은 #6.

## #6 대기열이 저장되지 않는다 — 저장 형식 3 (버그)

> CLI 로 `wait` 를 하면 대기 번호가 나오는데, 다음 명령에서 `waitlist` 를 보면 비어 있고 취소해도 승격이 안 된다.

기대 동작
- `storage.save` 는 늘 **형식 버전 3** 으로 쓴다. 형식 3 = 형식 2 에 다음을 더한 것:
  - `"waitlist": [{"id", "resource", "member", "start", "end", "attendees", "created_at"}, ...]` — 등록 순서.
  - `"next_ids"` 에 `"waitlist"`: 대기 번호는 지운 번호를 다시 쓰지 않는다(저장·읽기를 거쳐도).
  - `"teams": [{"id", "name", "monthly_credits", "overage_price", "members": [회원 id, ...]}, ...]` — `overage_price` 는 금액 문자열(예 `"2.50"`) 또는 `null`.
  - 예약마다 `"account"`, 원장 항목마다 `"account"`.
- `storage.load` 는 형식 1·2·3 을 읽는다. 형식 1·2 는 대기열·팀이 없는 것으로, 모든 예약·원장 항목의 계정은 `member:<회원 id>` 로 읽는다. `version` 이 정수 1·2·3 이 아니면(4 이상, 0, 문자열 `"3"`, 없음 등) `StorageError`. 형식 3 에서 없는 회원·팀·자원을 가리키면 `StorageError`.
- 형식 1·2 파일을 읽어 저장하면 정보가 하나도 사라지지 않아야 한다(다시 읽으면 같은 예약·반복 예약·원장·알림·잔액).
- README 의 저장 절과 storage 모듈 설명을 고친다.

## #8 예약 변경 시 크레딧이 다시 계산되지 않는다 (버그)

> 1시간 예약을 3시간으로 늘렸는데 크레딧은 1시간치만 빠졌다. 반대로 줄여도 돌려받지 못한다.

기대 동작
- `move` 는 새 시각의 비용을 지금 비용 규칙(`credits.cost`, 비수기 할인 포함)으로 다시 계산해 `booking.charged` 를 바꾼다. 청구·환불은 그 예약의 계정(#5)으로 가고, 원장 항목의 `note` 는 `"move"` 이다.
- 새 시작이 원래 시작과 **같은 달**이면 차액만 다룬다: 늘면 차액을 청구(초과 사용이 안 되는 계정은 그 달 잔액이 차액 이상이어야 하고, 아니면 `InsufficientCredits`), 줄면 차액을 환불, 같으면 원장 기록 없음.
- **다른 달**로 옮기면 원래 달에 원래 청구액 전부를 환불하고 새 달에 새 비용 전부를 청구한다(새 달 잔액으로 검사).
- 실패하면(`InsufficientCredits` 포함) 예약도 원장도 바뀌지 않는다.
- CLI `move` 의 출력(`ID START END CHARGED`)에는 새 청구 크레딧이 나온다.
